# AGENTS.md — общие правила для всех, кто строит систему

Этот файл читают все агенты и люди в команде (Claude Code, Codex, Cursor и др.). Если ваш инструмент читает только `CLAUDE.md`, там стоит ссылка сюда.

## 1. Что строим

AI-агент путешествий для трека Островка «О!дин запрос»: одно сообщение человека → вдохновение → подбор → сравнение → корзина → имитированная оплата → жизнь после покупки.

Архитектура — гибрид: код всегда собирает варианты сразу (быстрый путь, 2–4 с); если вариант очевидно не попадает в запрос, открытая модель думает до 30 с и зовёт те же инструменты (глубокий путь); код проверяет каждую цифру; оплату делает человек кнопкой.

Источники правды, по старшинству:

1. `AGENT_PLAN.md` — принятые решения (таблица № 1–36) и технический контракт (раздел «Technical contract»). Обязателен.
2. `docs/ARCHITECTURE.md` — схема одного хода, диспетчер, инструменты, данные.
3. `docs/IMPLEMENTATION_PLAN.md` — потоки работ W0–W12: файлы, договоры, тесты, критерии готовности, порядок, что режем.
4. Текст issue.

Конфликт между ними или нужное решение, которого нет, — **не решайте сами**: комментарий в issue с вопросом и вариантами, метка `status:blocked`.

## 3. Как запустить

```sh
uv venv --python 3.11 .venv && uv pip install -r requirements.txt
cp .env.example .env            # вписать OPENROUTER_API_KEY — только сюда
.venv/bin/python -m pytest tests -q                    # все юнит-тесты, ~5 мин
.venv/bin/python -m agent.server --debug --flags stage3,guide   # API + http://127.0.0.1:8787/debug
.venv/bin/python -m agent.server --fixtures                     # без модели: ответы-фикстуры договора (для интерфейса)
```

Перед PR — **полный** прогон `pytest tests -q`, хвост вывода — в описание PR.

## 4. Работа через issues

Каждая задача — issue. Метки статуса (ровно одна на issue):

| Метка | Значит | Кто ставит |
|---|---|---|
| `status:ready` | можно брать | ведущий |
| `status:waiting` | ждёт закрытия зависимостей («Зависит от» в issue) | ведущий; снимает, когда зависимости закрыты |
| `status:in-progress` | взято в работу | исполнитель — **сразу, как взял** |
| `status:review` | PR готов к проверке | исполнитель |
| `status:changes-requested` | ведущий вернул с замечаниями | ведущий |
| `status:blocked` | нужен ответ или решение человека | кто угодно, с комментарием |

Ещё метки: `W0`…`W12` (поток из плана), `must` / `should` / `could` (порядок резки), `lead-only` (делает только ведущий: живые вызовы моделей, закрытый бенчмарк, слияния), `infra`, `v3` (класс провала из `docs/FAILURES_V3.md`), `epic` (поток целиком — **не брать**, брать задачи из его чек-листа). Сводка всех задач — issue-трекер с меткой `tracker`.

### Взять задачу

1. Только issue с `status:ready`, без исполнителя, без `lead-only` и без `epic`; зависимости («Зависит от») закрыты.
2. Сразу: назначить себя (`gh issue edit N --add-assignee @me`), сменить метку на `status:in-progress`, комментарий: `Взял: <кто/какой агент>, ветка <ветка>`.
3. Одна задача на агента одновременно.

### Сделать

- Одна задача — одна ветка — один PR: ≤ ~3 ч работы, ≤ ~400 строк без сгенерированных файлов. Выходит больше — остановитесь, напишите в issue, ведущий разобьёт.
- Ветка от свежего `main`: `<ключ>/<коротко>` (например `w12a/slots-core`, `v3-2/direct-only`).
- Трогать только файлы своей задачи (они названы в issue). Общие файлы — `agent/engine.py`, `agent/server.py`, `agent/steps.py`, `agent/guards.py`, `skills/trip-agent/schema/understand.schema.json`, `skills/trip-agent/understand.md`, `skills/trip-agent/rules.json`, `skills/trip-agent/turns.json`, `agent/contracts/*.schema.json`, `AGENT_PLAN.md` — правьте минимальной вставкой и перечислите в PR.
- Меняете договор (состояние, схемы карточек, ответ API, инструменты мока, схемы БД) — обновите раздел «As built» / контракт в `AGENT_PLAN.md` и фикстуры в том же PR.
- Новые зависимости — только через ведущего (комментарий в issue).

### Горячие файлы — как не конфликтовать

| Файл | Правило |
|---|---|
| `skills/trip-agent/rules.json` | новые секции — **только** в `skills/trip-agent/rules.d/<тема>.json` (после #27); в `rules.json` — точечная правка существующей секции |
| `agent/guards.py` | новые проверки текста — в `agent/claims/<тема>.py` + одна строка регистрации (после #28); в `guards.py` — только правки существующих проверок |
| `agent/steps.py` (4,5 тыс. строк), `agent/engine.py` | новая логика — в новом модуле; в этих файлах — только вызов в одной точке |
| `skills/trip-agent/understand.md`, `understand.schema.json` | промпт на пределе строк: сначала страховка кодом. Если правка нужна — перед началом `gh pr list --search "understand in:title,body"`; есть открытый PR с ними — дождитесь слияния и перебазируйтесь |
| `evals/cases/*.json` | перегенерировать **только** кейсы своих карточек; новые кейсы — новые файлы |

Перед `status:review` — `git rebase origin/main` и полный `pytest`.

### Сдать

PR в `main`, заголовок `<ключ задачи>: <что изменилось>` (например `W12a: …`, `v3-2: …`), в описании:

```
Closes #N

## Что изменилось
## Договоры (схемы, API, AGENT_PLAN) — что и где
## Общие файлы — что и зачем
## Проверка
<хвост вывода pytest tests -q>
<если были живые прогоны: модель, провайдер, цифры>
## Риски / что не сделано
```

Метка issue → `status:review`. Черновой PR (draft) можно открыть раньше.

### Проверка ведущим

Ведущий (оркестратор) проверяет каждый PR как судья: тесты, соответствие решениям и контракту, зоны файлов, честность данных, инварианты из раздела 5.

- Всё в порядке → слияние (squash), issue закрывается.
- Есть замечания → комментарий с нумерованным списком, метка `status:changes-requested`. Исполнитель **сам** берёт возврат: правит в той же ветке, отвечает на каждый пункт («1 — исправлено в abc123», «2 — не согласен, потому что …, вот проверка»), снова ставит `status:review`.
- Сливает в `main` только ведущий. Прямые пуши в `main` запрещены.

## 5. Инварианты продукта (нарушение = возврат PR)

1. **Цифры считает и пишет код.** Модель не придумывает цены, время, даты, итоги. С потока W12 (решение 36) модель пишет только метки (`{price:v2}`), любая цифра в сыром тексте модели — блок.
2. Факты — только из инструментов (мок, открытые данные). Модель не ходит в веб.
3. Состояние держит код; модель без памяти между вызовами.
4. Всё, что видит человек, — по-русски; инструкции карточек — по-английски.
5. Тон лёгкий, ≤ 1 шутки в ответе; о деньгах, рисках, отмене и в жалобах — без шуток.
6. Личные данные — неявно: никаких «вы смотрели / в прошлый раз вы» (решение 32).
7. Скидка — только из данных мока (решение 33). Компенсации не обещаем (решение 35).
8. Нет данных — честное «нет данных», ничего не выдумываем. Синтетика помечена `source = synthetic` и названа синтетикой на демо.
9. Модели продукта — открытые веса через OpenRouter, провайдер закреплён; фактические модель и провайдер — в трассу.

## 6. Тесты

- `tests/` — без сети, без моделей, без реальных `codex` / `claude`: только `FakeBackend` и фейки.
- Новое поведение — новый тест. Нельзя удалять, пропускать или ослаблять тест, чтобы стало зелёно.
- Тесты со временем (`turn_ms < …`) чувствительны к нагрузке: падение на перегруженной машине — перезапустить тест отдельно, в PR написать.

## 7. Закрытый бенчмарк — `evals/bench/`

Репозиторий публичный, поэтому это правило чести:

- **Не открывайте** `evals/bench/**` (брифы, кейсы, сценарии, отчёты), если вы меняете агента.
- Ничего оттуда не попадает в промпты, примеры, списки подсказок, наши кейсы и тесты.
- Запускает бенчмарк только ведущий, на записанном коммите. Класс провала оттуда → наши новые кейсы своими словами.

## 8. Секреты и платные вызовы

- Ключи — только в `.env` (gitignored). Не печатать, не логировать, не коммитить.
- Живые вызовы моделей (evals, smoke) стоят денег: только если это прямо сказано в issue; модель, провайдер и стоимость — в PR.

## 9. Стиль

- Python 3.11, зависимости из `requirements.txt`, HTTP — stdlib `http.server`, без фреймворков.
- Пишите как соседний код; без попутных переименований и форматирования чужого.
- Коммиты — одно предложение о том, что изменилось в поведении системы (как в `git log`).
