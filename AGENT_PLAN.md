# План: агент трека «О!дин запрос»

Решения приняты в интервью 2026-10-24. Решение, которое нужно поменять, сначала согласуй с владельцем репозитория. Прежний проект «от двери до двери» (`SYSTEM_PLAN.md`, `skills/trip-planner/`, `system/`) удалён 2026-10-28, чтобы не путать команду; он остаётся в истории git, его проверки живут в `agent/checks.py`, фикстуры — в `tests/fixtures/trip_planner/`. Правила команды — `AGENTS.md`; схема — `docs/ARCHITECTURE.md`; потоки работ — `docs/IMPLEMENTATION_PLAN.md`.

## Цель

Скилл, с которым дешёвая модель **DeepSeek V4.1 Flash** стабильно и предсказуемо проводит пользователя от одного сообщения до имитированной покупки поездки (трек Островка «О!дин запрос»: вдохновение → выбор направления → подбор → сравнение → сборка → покупка → после покупки).

Главная метрика: **минимум касаний пользователя без потери качества подбора**. Дешёвые вызовы модели — следствие, не цель.

### Режим «гид» (решения 23–26)

Turn with free text (no button action), flag `guide` on:

1. `understand` and patch validation run as today; the route the pipeline would take runs its steps as today (the default plan), but `present` is not called.
2. Guide round 1 (Flash, reasoning off — decision 24, card `guide`, prompt `skills/trip-agent/guide.md`): input = compact context (today, stage, the brief's set fields with sources, profile home city, what is on screen with key facts, the last 4 exchanges, this message, the understand reading, the default plan's results compacted: variants / destinations / info facts, risks, relaxed notes, transport gaps, budget fit). Output JSON `{calls: [{tool, args}], reply: {message, show, recommended_id, question} | null}`.
3. `calls` non-empty → code runs the tools (in parallel where independent) and round 2 sees their compact results; at most 2 tool rounds, then a reply is required.
4. The reply goes through the card guards (numbers only from this turn's facts and tool results, change and promise claims, tone, Russian); one fix-up round with the issues; still failing → the pipeline's `present` card on the same results (or its code text).
5. Response: `message` from the guide; cards from the default plan or the tool results the guide chose (`show`); actions and chips built by code as today.

Tools wrap existing steps, compact in and out: `rebuild` (brief overrides: dates, nights, party, prefs, destination; returns variants), `find_savings` (levers priced by code: other start days, fewer nights, cheaper hotel class or district, no free cancellation, cheaper transport — connecting or train —, similar cheaper places; each with its total and difference), `check_road` (direct / connecting / train for the pair and dates), `find_destinations` (wishes, budget, month, transport overrides), `place_info` (sights, distances, climate and best time, hotel terms), `compare` (two or three shown variants). Facts the guide may cite come only from these results and the screen. Budget: the whole turn ≤ 15 s; time per round and per tool goes to the trace.

As built: guide mode (2026-10-25, branch `guide`). Flag `guide` (`agent/flags.OPT_IN_FLAGS`: in no preset, `--flags guide` / `TRIP_AGENT_FLAGS=stage3,guide`; `Flags.as_dict()` lists it only when on, so a flag-off engine answers byte-for-byte as before). `agent/guide.py`: `eligible` (a free-text turn — no button, no Jev-routed reply — whose route ends in a card of `rules.json guide.cards`: variants, update, destinations, compare, info, fallback; aftercare, cart, checkout and payment stay code), `run_guide(engine, ctx, failure, code_message)` → True or False (the pipeline path). The engine (`Engine._guide`) snapshots the screen at the start of the turn (`screen_snapshot`), runs the route's steps as today and, in guide mode, keeps a `no_data` StepError of a step as the default plan's `failure` (the guide's to solve; on fallback it is raised again — the same honest no_data answer) and a code answer (`_check_noop_rebuild`) as `code_answer`. Context (`build_context`, card input shape `evals/card_inputs.py` «guide»): today, stage, brief (`Brief.values()`), assumed, assumptions, home_city, screen (shown variants with key facts, places, cart), history (last 4 exchanges, agent texts cut to 300 chars), message, reading (intent, patch, refs, info_question), default_plan (status ok / failed / code_answer, variants compacted by `compact_variant` — whitelisted keys: totals, dates, nights, both legs, hotel, risks, gives_up, a fact whitelist —, recommended_id, changes, questions, destinations, info facts, comparison, transport gap, other places, notes, wishes cheaper / other_dates / other_place / best_time, buttons), round, tool_results; prompt + voice + schema form the stable system prefix, the state is the user message; `fit_context` cuts to `guide.max_context_chars` (24 000). Measured on the committed data: a new trip 4.6 k chars, «подешевле» with savings 9–13 k, «ещё дешевле» 18 k, a dead end 2.9 k, an info turn 10 k; the system prompt 12.2 k. Loop: `guide.auto_tools` runs find_savings by code before round 1 when the wishes hold «cheaper» (one model round less); a dead end (`dead_end`: the default plan failed with no_data, built only stays for lack of a road, or the turn asks about a failure that still stands — nothing on screen, the last turn's no_data or guide dead end) gets its likely fixes by code too, from the search results and `ctx.transport_gap` (no new search code): direct-only with no direct flight both ways but connecting ones → check_road + rebuild `prefs.direct_only false`; no flight but a train (or `plane_fixed`) → rebuild by train (scope flights → trains); `train_fixed` → by plane; no hotel under the filters → one rebuild per filter the person set (meals any, stars −1, district any, free cancellation any; filters they never set relaxed in each, the road fix rides along); ≤ `max_calls_per_round` auto calls in parallel, marked `auto`, rebuilds that build nothing left out unless none built; `default_plan.dead_end {why, auto_fixes}` tells the guide, which then answers with whole trips in one call (Калининград from Новосибирск direct-only, 4★, all inclusive: check_road «прямых нет, с пересадкой 15 (от 36 370 ₽)» + rebuild direct_only false, meals any → 125 520 ₽; the stars rebuild builds nothing); round 1; `calls` (≤ 3 per round, run in parallel on session copies) → round 2; at most `max_tool_rounds` (2) tool rounds, then the last round must reply. Tools (each on `_sub_ctx`: a copy of the session — brief, variants, shown, a copy of the results dict; searches merge back as cache only, `engine:*` state never): `rebuild {set, unset}` (allowed patch paths; `dates.shift_days` resolved against the trip's dates; a new start / nights drops the stale end; steps apply_patch, search, build_variants, check, upsell; `as_proposals` re-marks what the guide's patch changed — and this turn's understood patch did not say with that value — as source "inferred", so later turns, chips and the budget fit treat it as the agent's offer; find_destinations the same), `find_savings {from_id?}` (from the cheapest variant of the set on screen: other start day ±3 via the flex window, the two cheapest tried; −1 night, −2 with ≥ 5 nights; a cheaper hotel — stars −1, district any, no free cancellation, meals any, `hotel_cap` below the current stay —; −1 night + that hotel; connecting flights when the user fixed direct; the train when the pair has one; up to 3 similar places by the destination's tags, its country first, only of the trip's class (`same_class`: abroad vs at home from the origin's country, and the same `main_trait` — the catalog kind city / nature, else the first of sea, mountains, nature, city among the tags; prefs.domestic or traits the person set decide instead; none qualify → no places — Стамбул no longer gets Казань or Нижний Новгород), quoted for the same dates — 6 by plane, 3 by train; each lever `{lever, variant_id, total_rub, saving_rub, change_ru, gives_up_ru}`, levers that build the very same trip are merged, `not_cheaper`, `current.price_parts` tickets / stay / transfers; lever variants carry `dates_shifted_days` / `nights_changed_from`, a long train its leave day and time on board in code words), `check_road {to?, from?, date?, back_date?}` (flights on the day, direct / connecting counts and from-prices, nearby days with direct flights ±3, trains when the pair has them, `line_ru`), `find_destinations {set, unset}` (destination unset; steps apply_patch, find_destinations, quote_destinations), `place_info {question, destination?}` (step_info_lookup + the place record + best months, pruned to 3 500 chars), `compare {ids}` (comparison_rows). Bad args come back to the model as `{ok: false, error}`; a tool exception, a guide call over the time left, an LLMError or a transport failure → fallback. Tool variants get ids `custom-11…` (titles «На ночь короче», «Отель попроще», «Поездом»…). Reply (`schema/guide.schema.json`): `{calls, reply: {message, show variants|destinations|comparison|none, recommended_id, question {text, field?, choices [{label, value}]} | null}}`; `resolve_show` takes the set that holds recommended_id (the default plan's, the screen's or one tool call's; a savings set shows the chosen lever first plus two more). Guards (`guard_input` + `check_reply`): `check_card_output` of the matching present card on a pool = the shown items as `items` + common keys + changes (default + tools) + facts (default plan, screen, every tool result, info facts); the length rule is `guide.message_chars` [40, 1100] (+20 %), ≤ 1 question in message + question, `savings_claim` blocks «дешевле не нашлось» after find_savings found a lever or a place, unknown recommended ids / nothing to show block; a blocked reply whose only issues are formal (`too_many_questions`) is first repaired by code (`repair_questions`: the final question — the reply's question object, else the last question sentence — stays, the other question sentences go; fewer than 2 sentences left → no repair) and the guards run again (`g.repaired`); otherwise one fix-up round with the issues (rerun_system), then fallback. Commit (`commit`): the shown set becomes `session.variants` and `shown`, the brief of the recommended tool variant becomes the session brief, its results / districts / upsell go to the response; destinations are remembered and recorded as shown; a question with a valid field becomes a `q_guide` button question (else its text joins the message); places the message names get choose_destination actions; code notes are dropped (the guide got them). Guide calls do not count in `max_flash_calls_per_turn` (`budget.guide_calls`), the fallback present card does. Trace: `trace.guide` {rounds [{round, ms, latency_ms, usage {input, cached, output, reasoning}, context_chars, calls, reply} — a timed-out / failed round {round, ms, error}], tools [{call, tool, args, ms, ok, levers_ms}], context_chars, dead_end, repaired, rejected (debug sessions only: each blocked reply's message, question, show, recommended_id, issues), speculative {card, started_ms, used, discarded, ms_at_discard | waited_ms, ms}, fallback, used, show, recommended_id, ms}, `timings_ms.guide` and `guide_tool<N>_<tool>`, debug `guide`; level 3 reports `guide_turns`, `guide_used`, `guide_fallbacks` per scenario and `guide_fallback_rate`. Budget: `guide.turn_budget_s` 15 − `fallback_reserve_s` 3 from the turn start — or − `speculative_reserve_s` 0.5 while the speculative present is in flight. Speculative present (`guide.speculative_present`, on): `Engine._present` is split into `_present_prepare` (main thread: chips, the card input, before_present hooks) → `_present_call` (the model call, the guards, one rerun on a detached `PresentRun`: its own budget counters and call / hook / note / jev records, no ctx) → `_present_finish` (main thread: records and output into the turn); in guide mode, when the default plan built a card that needs a model call (no failure, no code answer), `_speculative_present` prepares it (the prepared shown labels / chips / card input are kept in the run and the turn's restored, so the guide's context is unchanged) and runs `_present_call` in a daemon thread — HTTP-bound, it overlaps the guide's calls (the OpenAI SDK / httpx client is thread-safe; the guide already calls the backend from worker threads). Guide used → the run is discarded (its call is not the turn's; trace `speculative.discarded`); guide failed → `_finish_speculative` waits for it at most max(the time left of `turn_budget_s`, `speculative_wait_min_s` 3) and finishes the pipeline path with it (not done → degraded code texts). A guide failing at round 1 then costs about max(guide, present), not the sum. Flag off: `_present` = the three parts in a row, byte-identical answers. `guide.thinking` off (decision 24; a setting), temperature 0.6, max_tokens 1800 (rules.json; the card is loaded by `skill_loader` as `extra_cards["guide"]`, outside turns.json). In process (no model): a new trip ~0.6 s; «подешевле» ~5 s (the default plan's own budget fit ~3 s + find_savings 0.9–1.8 s); rebuild 0.1–0.4 s, check_road 40 ms, find_destinations 0.4 s, place_info / compare < 10 ms. - Temperature and adaptive thinking (level 2: 47 cases × 5 runs, 3 runs per config, configs run concurrently, 2026-10-25): provider default temperature (1.0) → 46.7/47 cases fully passing, 3.7 guard reruns per 235 calls, p50 1556 ms; temperature 0.3 for understand / 0.6 for present cards → 46.3/47, 1.7 reruns, p50 1567 ms; thinking `low` only for images and understand messages ≥ 60 chars → 46.0/47, 3.0 reruns, those calls p50 +0.6 s and p95 +2.1 s with no quality gain on them (135/135 passed in every config). - Image + text (≈ 515 input tokens): thinking off 1.6–1.8 s, ≈ $0.00013; `low` 2.6–5.4 s with up to 750 reasoning tokens. A famous landmark (Hagia Sophia) → confidence 0.99; a landscape (Big Sur coast) → right place at 0.55 off / 0.85 low, traits correct. Free-text trait lists come back unless the schema enforces enums.
- Jev decision with 2 questions: 347 ms, $0.00002; answers matched expectations (family + «недорого» → district `quiet` 0.98; «budget stated precisely» 0.04).

## 3. State

As built (W5a): optional `PastTrip` fields `order_id`, `price_rub`, `party`, `stars`, `transport`, `destination_kind`, `paid_at` retain compatibility with old profile JSON. A successful pay appends the order once per profile/order id. The `profile_history` turn-end analytics hook writes private `views(profile_id, kind, ref_id, at, source)` to `ostrovok_state.sqlite` (`kind`: destination/hotel/variant; `source`: shown/opened/carted); anonymous sessions and failed turns are not recorded. No history is added to prompts or insights.

`agent/state.py`, pydantic v2. One `Session` per conversation, persisted as JSON in `runtime/sessions.sqlite`.

```
Field[T] = { value: T | null, source: "user"|"profile"|"pattern"|"default"|"inferred", confidence: float | null }

Brief:
  origin:        Field[{ city: str, iata: [str] }]
  destination:   Field[{ id: str|null, name: str, country: str|null }]
  traits:        Field[[DestinationTrait]]          # wishes for "where": sea, mountains, warm, city, nature, ...
  dates:         Field[{ start: date|null, end: date|null, month: int|null, window: {from: date, to: date}|null,
                         nights: int|null, flexible_days: int }]
  party:         Field[{ segment: "solo"|"couple"|"family"|"friends"|"other", adults: int, children: int,
                         children_ages: [int]|null, pets: [str] }]
  budget_rub:    Field[{ max: int|null }]
  scope:         Field[["flights"|"trains"|"stay"|"transfers"]]
  prefs:         Field[{ meals: "any"|"none"|"breakfast"|"half_board"|"full_board"|"all_inclusive",
                         free_cancellation: bool|null, stars_min: int|null, direct_only: bool|null,
                         max_travel_hours: float|null, district: "any"|"lively"|"quiet"|"family"|"walkable",
                         beach_max_m: int|null, center_max_m: int|null,   # metres to the city centre
                         transport: "any"|"plane"|"train",
                         arrive_before: "HH:MM"|null,   # outbound arrival, local clock at the destination
                         no_night_flights: bool|null,   # no night legs, flights and trains: none leaving/landing in
                                                        # ranking.night_window, no train on the move at 03:00
                         domestic: bool|null }]         # inspiration: destinations in the origin's country
                 # ranking: user-set arrive_before / no_night_flights / free_cancellation (refundable
                 # fares) filter tickets, relaxed per direction with risk relaxed_pref / non_refundable_only;
                 # a scope without "stay" builds tickets-only variants (no hotel, no transfers)
  constraints:   Field[[str]]   # hard constraints, enum-like tokens: "pet:dog", "accessible", "no_night_flights", ...
  mood:          Field[[str]]   # "relax", "party", "culture", "active", "romantic", "kids_fun"

Session:
  id, created_at, now (injectable clock; evals pin it), profile_id
  brief: Brief
  stage: "inspiration"|"selection"|"cart"|"checkout"|"ordered"|"aftercare"
  shown: { destinations: [ShownItem], variants: [ShownItem], hotels: [ShownItem] }   # short labels "1","2","3" for references
  results: cached search results by key (search params hash) with fetched_at
  variants: [Variant]           # built by code
  chosen_variant_id, cart_id, order_id
  pending_questions: [Question]
  history: last 6 user messages verbatim + last 3 agent messages (text only)
  trace: per-turn records (calls, hooks, timings), capped
```

`Variant` (built by code): `id` (`cheapest|fastest|comfort` or `custom-N`), `steps` (flight/train/transfer/stay steps compatible with `agent/checks.py`), `totals` (`rub`, `door_to_door_hours` both ways, `out_hours` / `back_hours` one-way door-to-door, 1 decimal, null when that direction is absent; `prefs.max_travel_hours` is a one-way limit checked against them), `facts` (computed numbers the card may cite), `sacrifices` (computed diffs vs the other variants), `risks` (computed: connection slack, night arrival, non-refundable, long transfer...), `not_for` (computed from district scores and hotel policies), `fit` (0..1 with per-criterion breakdown), `upsell_candidates` (rule hits from `upsell.json`, each with its reason).

As built (v3-11): `fit` reduces a night-arrival variant's score for mood `relax`, families/children, or travellers aged at least `ranking.night_senior_age` (65) in the profile. `ranking.night_relax_penalty` / `night_family_penalty` / `night_senior_penalty` default to 0.15 / 0.2 / 0.2; the largest applicable reduction is used once. Local outbound arrival and the transfer's arrival at the hotel use `ranking.night_window`; return arrivals do not count. `fit.breakdown.arrival_time = 0` explains the reduction. Profile age or saved birth dates on the trip start date (session date when unknown) become only an internal ranking boolean; they are not put into the brief or model input. Night options and their risks remain visible; existing hard night-travel filters are unchanged.

The model never produces prices, times or totals. It only selects ids and writes text; every number it writes must exist in its input (checked by a hook).

Every card gets one JSON object as the user message. Common keys: `today` (ISO date), `stage`, `brief` (values only, `Brief.values()`), `assumed` (brief paths whose source is not `user`, e.g. `["origin.city", "party.segment"]`), `assumptions` (the chips shown with this answer: `[{"field", "label"}]`).

- `understand`: common keys + `shown` (`[{"label": "1", "kind": "destination|variant|hotel", "id", "title"}]`), `pending_questions` (`[{"id", "field", "text", "choices": [label]}]`), `history` (`[{"role": "user|agent", "text"}]`, ≤ 6 user + 3 agent), `message` (the new user text), `has_image` (bool; the image itself goes as an image part).

- `present.compare`: common keys + `items` (2–3 variants as above) + `dimensions` (the brief's priorities in order).
- `present.info`: common keys + `question` (the user's question) + `facts` (the looked-up records; empty when nothing was found; variant records carry legs with local dates + times, the stay's check-in / check-out dates + times and `nights_without_stay`; a paid order carries `if_cancelled` (code-computed refund / loss); open cart / order warnings come as a `warnings` record the card never contradicts).

### Foundation decisions (2026-10-25)

1. Provenance is per sub-field: `Field.sub_sources` / `sub_confidence`, read through `Brief.source_of(path)` / `confidence_of(path)`; engine assumptions go through `agent.state.assume(brief, path, value, source, confidence)`, never through `apply_patch`.
2. After every patch the engine normalises `party` from `segments.json` defaults (e.g. `couple` → 2 adults) with `assume(..., "default")` for the sub-fields the user did not give.
3. Photo entry: when a request has an image, the engine runs `image_match` before route matching. `image.place.confidence ≥ rules.image.place_min_conf` (0.8) and the place resolves in the catalog or the geocoder → `assume("destination.name", …, "inferred", conf)` → route B. Between `rules.image.confirm_min_conf` (0.5) and 0.8 → destinations route with the recognised place first plus a confirmation question. Below → traits only.
4. `choose_variant` puts the variant straight into the cart (one tap); `add_to_cart` is for extras.
5. Offer ids are deterministic and encode their parameters, so the mock rebuilds an offer from its id alone (a cache is only an optimisation).
6. `dates.shift_days` with no concrete dates: before `apply_patch` the engine resolves the shift against the dates of the variants currently shown and sends concrete `dates.start/end`; with nothing shown it asks.
7. Children's age buckets send one representative age; exact ages arrive at checkout and the `after_travellers` hook re-checks the cart.
8. No placeholder offers: upsell kinds are only what the mock sells — `transfer`, `early_checkin`, `room_upgrade` (incl. high floor), `meal_upgrade`, `flexible_fare`. The insurance rule is dropped.
9. Early check-in is not a cart item (the mock sells it as an order action): when the user accepts the early check-in add-on before paying, the engine remembers it and calls `order_request_early_checkin` right after `pay`, then reports the result in the same answer.

## 5. Turn pipeline

1. Input: free text (+ image) or a UI action (button, chip, card choice). Actions map to brief patches or engine commands deterministically, without `understand`.
2. Free text: Jev routing first (when enabled): short replies to pending questions or references to shown items are resolved without Flash when confidence ≥ the threshold in `rules.json`; otherwise `understand` (Flash).
3. Validation hook on the patch; the engine applies it, records provenance, computes affected fields, and picks the route.
4. Steps run (code calls MCP and open-data tools). Prefetch hooks may already hold results.
5. Validation hooks on results (`agent/checks.py`: chain, buffers, budget, dates; segment fit). Failure → one rerun of the affected step with the issue; still failing → present the best available with the issue stated honestly.
6. Sensitivity check (stage 2+) and Jev ask-or-assume (stage 3+) decide questions (≤ 2) and chips.
7. `present.<card>` (Flash) writes the text. Semantic hook (Jev, stage 3+) + deterministic checks (numbers ⊂ input numbers, ids exist, ≤ 1 joke heuristic, upsell only from candidates) → one rerun on failure.
8. Response assembled by code (section 6); analytics hook logs events; prefetch hooks start background work for the likely next step.

Budget: ≤ 2 Flash calls per turn (plus at most one rerun per card on a failed hook); recorded per turn in `trace`.

## 6. Response contract (engine → UI)

As built: GIF input (W10a) is decoded by `agent/frames.py` before the HTTP server calls the engine: the first frame, plus the middle frame when there are at least three frames, becomes one PNG (frames side by side). The `image` request field and the existing photo path stay unchanged. Invalid GIFs return HTTP 400; the image size limit also applies to the resulting PNG (HTTP 413).

`agent/contracts/response.schema.json` (JSON Schema draft-07), with fixtures in `agent/contracts/fixtures/` for every stage. HTTP API (`agent/server.py`):

- `POST /api/session` `{profile_id?}` → `{session_id}`
- `POST /api/turn` `{session_id, text?, image?: <data URL>, action?: {type, payload}}` → `Response`
- `GET /api/session/<id>` → session state (debug)
- `GET /files/<path>` → `.ics` and pages from `runtime/files/`
- `GET /debug` → `web_debug/index.html`

`Response`:
```json
{
  "session_id": "s_…", "turn": 3, "stage": "selection",
  "message": "Russian text",
  "chips": [{"field": "prefs.meals", "label": "с завтраком", "value": "breakfast", "options": [{"label": "…", "value": "…"}]}],
  "questions": [{"id": "q_party", "text": "Кто едет?", "field": "party.segment", "choices": [{"label": "вдвоём", "value": "couple", "recommended": true}]}],

  "comparison": null, "cart": null, "order": null,
  "actions": [{"type": "choose_variant", "label": "Беру этот", "payload": {"variant_id": "cheapest"}}],
  "files": {"ics": null, "page": null},
  "debug": {"stage_path": [], "calls": [], "hooks": [], "timings_ms": {}, "jev": [], "flags": {}}

```
Action types: `answer_question {question_id, value}`, `set_chip {field, value}`, `choose_destination {destination_id}`, `choose_variant {variant_id}`, `swap_hotel {variant_id, hotel_offer_id}`, `compare {variant_ids}`, `add_to_cart {variant_id, extras: [offer_id]}`, `checkout {travellers: [{name, birth_date}], contact}`, `pay {order_id}`, `order_action {order_id, kind: early_checkin|change_dates|add_transfer, params}`. `debug` is present only when the session is created with `debug: true`. ## 8. Data

Two committed read-only databases, built by `data_build/build_all.py` (resumable, cached raw downloads in `data_build/cache/`, gitignored; mirrors and retries for Overpass; Nominatim and Photon as fallbacks for geocoding; polite User-Agent and rate limits):

- `data/opendata.sqlite` — open data, read by the engine's open-data tools: `destinations` (id slug, names ru/en, country, lat/lon, kind, tags, airports, stations, short description ru, popularity), `climate` (destination × month: air max/min, sea temperature, rain days, sunny days; source Open-Meteo archive/marine, fetched_at), `airports` (OurAirports), `routes` (OpenFlights: origin, destination, carriers, stops), `districts` (per hotel osm id: POI counts in 500 m and nearest distances; scores lively/quiet/family/walkable 0..1; source, fetched_at).
- `data/ostrovok_catalog.sqlite` — the mock's inventory: `hotels` (real OSM names/coordinates/kinds + deterministic synthetic fields), `rooms`, `policies`, `insights_events` (synthetic log from a hidden preference model, flagged `source = synthetic`).
- Schemas in `data/schema/opendata.sql` and `data/schema/ostrovok_catalog.sql`. Every fact row carries `source` and `fetched_at`.
- Honesty: real = places, hotels' names/coordinates, districts, climate, airports, routes; synthetic = prices, availability, schedules, ratings, policies, insights. The README and the demo say so.
- Measured 2026-10-24 from the dev machine: Open-Meteo archive/marine, OurAirports CSV, OpenFlights `routes.dat`, CBR XML, Nominatim and Photon answer fast. Overpass is slow and flaky: a first round gave `overpass-api.de` 502 and 30 s timeouts on the kumi/private.coffee/mail.ru mirrors; a retry minutes later succeeded on `overpass-api.de`, `lz4.overpass-api.de` and `z.overpass-api.de`, but each tiny query took 32–36 s. So: one batched query per city (all hotel and POI tags for the city's bounding box at once, never one query per hotel), long timeouts, sequential requests with backoff across those mirrors, every successful response cached, resumable builds; fall back to Photon (`photon.komoot.io/api/?q=…&lat=…&lon=…&osm_tag=tourism:hotel` and amenity tags) with distance filtering only when Overpass stays down, and a district built from the fallback records `source = "photon"`.

Open-data tools (`agent/opendata.py`, called by code): `destination(id)`, `find_destinations(traits, month, origin_city, budget?, max_travel_hours?, segment?, limit)`, `climate(destination_id, month)`, `district_profile(osm_id)`, `airports_near(lat, lon)`, `geocode(name)` (catalog first, then Nominatim), `travel_time(origin_city, destination_id)` (routes graph + great-circle duration), `cbr_rates()` (live with cache, fallback to the cached rate with its date), `pois_rows(destination_id)` / `find_poi(destination_id, text)` / `find_poi_in_text(destination_id, text, cues)` (named sights and districts of table `pois`, matched by `agent/places.py`; one index per destination per instance).

`agent/hooks.py`: `register(event, fn, kind)`, events `after_understand`, `after_search`, `after_variants`, `before_present`, `after_present`, `after_travellers`, `turn_end`; kinds `validate` (blocking, returns issues), `prefetch` (background, results land in `session.results`), `analytics` (fire-and-forget). Hook verdicts go to `trace` and `debug`.

`agent/flags.py`: `sensitivity`, `jev_routing`, `jev_ask`, `jev_guard`, `prefetch`, `upsell`, `insights`; presets `stage1`…`stage5` per the activation order above; set via `TRIP_AGENT_FLAGS=stage3` or a comma list. Opt-in `guide` (guide mode, decisions 23–26) is in no preset: `TRIP_AGENT_FLAGS=stage3,guide`, `--flags guide`.

## 10. Evals

- Level 2 case `evals/cases/<id>.json`: `{id, category, card, input, image?, expect: [assertion], runs: 5}`. `input` is the exact card payload, produced by `python -m evals.build_inputs` from the engine with a pinned clock and the committed data (no model). Assertion types: `schema`, `path_equals`, `path_in`, `path_absent`, `path_present`, `max_items`, `regex_absent`, `numbers_subset`, `ids_subset`, `predicate` (named function in `evals/assertions.py`).
- Level 3 scenario `evals/scenarios/<id>.json` (and `evals/holdout/`): `{id, category, persona: {start_message, image?, profile, hidden: {facts, must: [predicate], nice: [str]}, behaviour}, max_turns}`. `must` predicates are checked by code on the final cart/order/state.
- Runner: `python -m evals.run --level 2|3 --set main|holdout --runs N --flags stageK --model flash|qwen|codex --out evals/runs/<ts>`. Raw transcripts → `evals/runs/` (gitignored); summary → `evals/reports/<ts>.json` and `.md` (committed): pass k/N per case, first recommendation in first reply, touches to a ready cart (every text, button, chip and card choice is a touch), hidden-requirement satisfaction, connection errors, calls per turn, latency p50/p95, cost, served model and provider, Jev fallback rate, fallback-card rate.
- Persona: `evals/persona.py` drives Sonnet 5.5 through the Claude Code CLI (section 2) with `evals/skills/persona/SKILL.md` as the system prompt; it sees the response rendered like the UI (message, questions with choices, chips, cards, actions) and answers `{"type": "text", "text"}` or `{"type": "action", "action": {...}}`. Unit tests use a fake `claude` executable.
- Sealed benchmark `evals/bench/vN/` (protocol in `evals/bench/README.md`): level-2 cases and level-3 scenarios written by an outside model from `BRIEF.md` alone; run only by the orchestrator, on a recorded commit, with `--set bench --bench evals/bench/vN` (runs and reports stay inside the version). Whoever changes the agent never opens it, and nothing from it goes into prompts, examples, cue lists, our cases or tests; a class of failure found there gets our own new cases in other words, and the next honest number needs a fresh version.
- Judge: the runner writes one packet per scenario to `evals/runs/<ts>/judge/<id>.md`; Opus subagents apply `evals/skills/judge/SKILL.md` and write `<id>.verdict.json`; `python -m evals.report --merge-judge evals/runs/<ts>` folds verdicts into the report.

## 11. Tests and rules for builders

- Unit tests: `.venv/bin/python -m pytest tests -q`. No network, no model calls, no real `codex` in tests; fakes only.
- Builders run the full suite before a PR (`AGENTS.md` §3); the lead runs every suite again when reviewing.
- Never skip or delete a test to get green; never invent data — degrade to an honest "no data" state and report it.
- Work goes through issues, branches and PRs (`AGENTS.md` §4); only the lead merges into `main`, nobody pushes to `main` directly.

## 12. Build order

1. **Foundation** (alone): venv and requirements; `agent/state.py`, `agent/env.py`, `agent/llm.py` (Backend protocol, OpenRouter backend, FakeBackend), `agent/jev.py`, `agent/flags.py`, `agent/skill_loader.py` (+ `turns.json` validation), `agent/contracts/response.schema.json` + fixtures, `ostrovok_mcp/contract.py`, `data/schema/*.sql`, the skill package skeleton with the card schemas, `tests/` scaffolding.
2. **Parallel**, each against the foundation: data (`data_build/`), the mock (`ostrovok_mcp/`), the engine (`agent/` steps, ranking, sensitivity, checks, hooks, prefetch, opendata, mcp client, sessions, profiles), the server + debug page + Codex backend, skill content v0 (`skills/trip-agent/`), evals (`evals/`).
3. Integration and stage 1 baseline run; then stages 2–5 and the improvement loop.

As built (v3-6): synthetic mock `Accessibility` adds `accessible_room` and `step_free_route` (deterministic by hotel_id; an accessible room implies a step-free route). `search_hotels.filters.accessible_room` filters before limit. Constraint `accessible` requires both facts, relaxes honestly if unavailable, and reads wheelchair/walker/stair/threshold cues from rules.d/accessibility.json. Variant and stay-info facts expose both plus `accessibility_synthetic`. Text claims are checked in agent/claims/accessibility.py. Public travel-agent response schemas are unchanged.
