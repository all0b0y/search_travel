# План реализации: гибрид «быстрый + глубокий путь», личные сигналы, жизнь после оплаты

Дата: 2026-10-28. Срок: 2 дня. Схема — `docs/ARCHITECTURE.md`, решения — `AGENT_PLAN.md` № 27–35.
Контракт `AGENT_PLAN.md` (Technical contract) остаётся обязательным: модель не выдумывает цифры, состояние держит код, тесты без сети и без моделей, всё, что видит человек, — по-русски.

## 0. Исходное состояние (проверено 2026-10-28)

- `main` = конвейер + режим «гид» (ветка `guide` влита 2026-10-28 вместе с последними правками гида): `agent/guide.py` (1 866 строк), карточка `guide`, 6 инструментов, спекулятивный `present`, бюджет 15 с, 2 круга, размышление выкл. Прежний проект (`system/`, `skills/trip-planner/`) удалён.
- Тесты: 1 934 проходят (2 мин 21 с); 1–4 теста со временем хода (`turn_ms < 1500`, `test_holdout2`, `test_long_trains`) падают на нагруженной машине (load average > 8) — и на `main` до слияния; отдельный issue.
- Слепой бенчмарк v3: сторона конвейера прогнана (уровень 2 — 36/40, уровень 3 — скрытые требования 89 %, первая рекомендация в первом ответе 95 %, касаний до корзины 3,89). **Сторона гида не прогнана.** Провалы конвейера на v3 ещё никто не читал — так и оставляем до прогона гибрида.
- Один `Backend` на движок (`Engine(backend=…)`), модель задаётся при создании. Для планировщика на другой модели нужна маршрутизация «карточка → бэкенд».
- `/api/turn` отдаёт один JSON в конце хода; `ThreadingHTTPServer` — поток событий (SSE) на нём делается без фреймворка.
- Профиль: `past_trips` есть (направление, месяц, год, сегмент, ночи), код их не читает. Просмотров, скидок, обращений, отложенных сообщений нет.
- Намерения `understand`: `new_trip, refine, answer, choose, compare, info, cart, checkout, post_purchase, smalltalk, out_of_scope` — жалобы нет.

### W1. Маршрутизация моделей по карточкам (~2 ч)

- `agent/llm.py`: `BackendRouter(default, by_card: dict[str, Backend])` реализует тот же `Backend.complete`; выбор по `req.card`. `FakeBackend` остаётся для тестов.
- `turns.json`: у карточки необязательные `model`, `provider` (закреплённый), `fallback` (`{"model", "thinking"}`). Валидация в `skill_loader.py`.
- `agent/engine.py::_default_backend` собирает роутер из `turns.json`; переопределение через env `TRIP_AGENT_MODEL_<CARD>` (для замеров) с записью в трассу.
- Запасная цепочка планировщика: основная модель → ошибка/таймаут → Flash с размышлением `low` → `present` конвейера. Каждая ступень — в трассу (`guide.fallback`).
- Кандидаты и провайдеры (проверено по OpenRouter 2026-10-28): `deepseek/deepseek-v4-pro-0813` → провайдер DeepSeek; `qwen/qwen3.8-2.4t-a95b` → Alibaba; `z-ai/glm-5.3` → Z.AI. Поддержку `reasoning` и `response_format` у закреплённого провайдера проверяет живой smoke-тест оркестратора, не юнит-тесты.

Тесты: роутер выбирает бэкенд по карточке; запасная цепочка срабатывает на `LLMError` и таймауте; модель и провайдер попадают в трассу.

### W2. Диспетчер `fast | deep` (~3 ч)

- Новый `agent/router.py::choose_path(ctx, session, plan) -> PathDecision{path, reason, signals, jev}`, вызывается в `engine.handle` **после** дефолтного плана (шаг 3) и **вместо** `guide.eligible` как условия запуска планировщика.
- Правила (по порядку, всё в `rules.json` → `router`):
  1. кнопка — диспетчер не вызывается;
  2. намерения `complaint`, `post_purchase`, `info`, `smalltalk`, `out_of_scope` → fast;
  3. первый ход сессии → fast (решение 30);
  4. повтор просьбы: нормализованный текст или та же правка брифа, что в прошлом ходе → deep;
  5. результат плана: `no_data`, все варианты выше `budget_rub.max`, есть риск `relaxed_pref` / `budget_fit` / `transport_switched` → deep;
  6. правка ровно одного поля из списка простых (`dates.shift_days`, `dates.nights`, `party.pets`, `prefs.meals`, …) и план собрался → fast;
  7. иначе Jev: вопросы `subtext` (подтекст / компромисс) и `enough` (хватает ли данных без рассуждения); deep, если `subtext ≥ router.subtext_min` или `enough < router.enough_min`; Jev недоступен → `router.jev_down` (по умолчанию deep).
- Причина решения — в `debug.calls` / трассу хода: `{"path": "deep", "reason": "budget_over", "jev": {...}}`.
- Данные для порогов: 40 размеченных ходов `evals/cases/router/*.json` (`{context, plan_summary, expect_path}`), из них ≥ 15 серой зоны. Пишет внешняя модель по брифу (не мы), разметка — двумя людьми или моделью + проверкой оркестратора.

Тесты: каждое правило отдельным кейсом; Jev `None` → `jev_down`; трасса содержит причину. Метрика: точность диспетчера на размеченных ходах ≥ 85 %, доля deep среди текстовых ходов — пишется в отчёт.

### W3. Планировщик: 30 с, 3 круга, модель по замеру (~3 ч + замеры)

- `rules.json` `guide`: `turn_budget_s` 30, `max_tool_rounds` 3, `thinking` из замера, `fallback_reserve_s` 4.
- `guide.md`: правило «сначала пойми, что человеку на самом деле нужно, назови это одной фразой» (это и есть «суть агента»), правила про скидки и личные сигналы (W5), без «вы смотрели».
- Новый инструмент `find_deals` (после W5).
- Замер кандидатов: наши кейсы гида уровня 2 (× 5) + v3 уровень 3 только на deep-ходах; метрики: скрытые требования, проходы проверок с первого раза, p50/p95 круга и хода, стоимость, доля запасного пути. Победитель → `turns.json` `guide.model`, запись в `AGENT_PLAN.md` «Measured …».

Готово: deep-ход p95 ≤ 30 с, запасной путь ≤ 5 % ходов, скрытые требования гибрида на v3 ≥ конвейера.

### W4. Поток событий: шаги и шутки (~4 ч, договор с интерфейсом)

- `POST /api/turn/stream` (тот же запрос, что `/api/turn`) → `text/event-stream`:
  - `event: step` `{"kind": "find_destinations", "line": "Ищу море подешевле на апрель и май", "joke": "…", "round": 1, "t_ms": 3200}`;
  - `event: response` — полный `Response`, как у `/api/turn`;
  - `event: error`.
  `/api/turn` остаётся без изменений (обратная совместимость, тесты, evals).
- `engine.handle(..., on_event=callable)`; `guide.run_tools` и цикл кругов зовут `on_event` перед каждым кругом и инструментом. Быстрый путь шагов не шлёт (или один «Собираю варианты»).
- `skills/trip-agent/steps.json`: на каждый тип шага (`think`, `rebuild`, `find_savings`, `check_road`, `find_destinations`, `place_info`, `compare`, `find_deals`, `check`) — шаблон строки со слотами (`{months}`, `{budget}`, `{city}`, `{to}`, `{dates}`) и 4–5 шуток. Слоты заполняет код из аргументов вызова; числа в строке — только из аргументов. Шутка выбирается без повтора в сессии (`session.used_jokes`).
- Ограничение решения 10: шутки шага `check` — про саму проверку, не про цены; в сессии с открытой жалобой шутки не шлём.
- Договор для интерфейса: раздел в `agent/contracts/README` + фикстура потока `fixtures/stream_deep.txt`.

Тесты: формат SSE; порядок событий (шаги до `response`); слоты без выдуманных чисел; без повторов шуток; при жалобе — без шуток.

### W5. Личные сигналы, скидки, первый ход (~5 ч)

**Данные**
- Профиль: `past_trips` → расширить до заказа: `price_rub`, `nights`, `party`, `stars`, `transport`, `destination_kind`, `paid_at` (обратно совместимо, все поля необязательные). Оплаченный заказ мока автоматически дописывается в профиль.
- `runtime/…views` (в `ostrovok_state`): `profile_id, kind (destination|hotel|variant), ref_id, at, source (shown|opened|carted)`. Пишет движок: показали → `shown`, нажали/спросили → `opened`, положили в корзину → `carted`.
- `deals` в моке (`ostrovok_mcp/deals.py`, детерминированные, `seed = sha256(destination|month)`): `{deal_id, destination_id, month, kind (hotel|package), pct, valid_from, valid_to, conditions_ru}`; **применяются в ценах мока**, поэтому карточка, корзина и заказ сходятся. Инструмент мока `search_deals(origin_city, month, destination_ids?)`.
- Сиды для тестов: 15 синтетических профилей (`data_build/profiles_seed.py`): новый; вернувшийся с 1–3 заказами; со «смотрел, не купил»; семья; бюджетный; любитель поездов. Помечены `source = synthetic`.

**Код**
- `agent/personal.py`: `signals(profile, views, today) -> Signals` (бюджетная полоса, обычный состав и ночи, транспорт, класс отеля, был в последние 12 мес, смотрел-не-купил с весом свежести) и `assume_from_signals(brief, signals)` через `assume(..., "profile"|"pattern")`.
- Первый ход «хочу куда-нибудь»: `step_find_destinations` без желаний → пул = сезон (климат месяца) × спрос (`insights_popular_destinations`) × личная близость × скидка; **три разных типа отдыха** (море / город / природа или по сигналам) — разнообразие и даёт попадание в топ-3. Исключаем места, где человек был в последние 12 месяцев.
- Вопросы на первом ходу (≤ 2 кнопками): выбирает чувствительность из уже существующего механизма; кандидаты — тип отдыха и бюджет.

**Проверки текста** (`guards.py`)
- `history_claim` (block): «вы смотрели», «вы искали», «в прошлый раз вы», «как и в прошлом году» — нельзя.
- `deal_claim` (block): «скидк», «акци», «дешевле обычного», «−N %» — только если у показанного элемента есть `facts.deal` и число совпадает.

Тесты: сигналы из профиля; наружу не уходит источник; скидка сходится в карточке, корзине и заказе; три разных типа на первом ходу; обе проверки в обе стороны (с отрицанием — не срабатывает).

### W6. После оплаты: проактивные сообщения (~5 ч)

- `agent/proactive.py` + таблица `outbox` (`runtime/sessions.sqlite`): `{id, session_id, order_id, kind (pre_trip|mid_trip|post_trip|ticket_update), due_at_utc, status (pending|sent|skipped|cancelled), sent_at, payload}`.
- На `pay`: три записи. `pre_trip` = выезд − 2 дня, 10:00 местного времени человека; `mid_trip` = 2-й день, 19:00 местного места отдыха; `post_trip` = день после возврата, 12:00. Смена дат заказа (`order_change_dates`) переносит записи; отмена — отменяет.
- Правила (`rules.json` `proactive`): тихие часы 22:00–09:00 (сдвиг, не пропуск), ≤ 1 сообщения в день, «не пишите мне / хватит» → понимание `post_purchase` с флагом отписки → все `pending` → `cancelled`, профиль `proactive_opt_out`.
- Текст: карточка `present.proactive` (Flash, `voice.md`, проверки чисел), вход — факты: направление, даты, погода из `climate`, время заселения, трансфер; запасной — шаблон кодом.
- Отзыв: ответ на `post_trip` → кнопки оценки 1–5 + текст → `feedback`; в `insights` уходит только обезличенное (оценка, направление, сегмент).
- Доставка: сообщение добавляется в историю сессии и уходит событием `event: message` в `GET /api/session/<id>/events` (SSE, держит соединение) или через `GET /api/session/<id>/inbox?after=<id>` (опрос — для интерфейса без SSE). Внешние каналы (Telegram, почта, push) — интерфейс `Notifier`, реализован только `ChatNotifier`; остальное — в список идей.
- Планировщик: поток в `server.py`, тик раз в 30 с, часы подменяемые (`clock`). Для тестов и показа: `POST /api/dev/clock {advance_hours}` — **только** при `TRIP_AGENT_DEV=1`, в продуктивном режиме 404.

Тесты: расписание от дат заказа и часовых поясов; тихие часы; перенос и отмена; отписка; одна отправка (идемпотентность при перезапуске); текст без выдуманных чисел.

### W7. Жалобы → компания (~4 ч)

- `understand`: намерение `complaint` + поле `complaint {order_ref?, item_kind?, what_ru, when?}`; страховочные подсказки кодом (`rules.json` `complaint.cues`: «не заселяют», «отменили рейс», «не приехал трансфер», «грязно», «обманули», «жалоба»).
- Маршрут `complaint` (fast, без планировщика): код определяет заказ (единственный оплаченный → он, иначе вопрос кнопками) и позицию; срочность — правилами (`urgent`, если поездка идёт сейчас и проблема в проживании / дороге). Не хватает факта — один вопрос.
- Мок: `support_create_ticket(order_id, item_id?, category, urgency, description_ru, contact)` → `{ticket_id, status: open, sla_hours}`; `support_get_ticket`; статусы `open → in_progress → resolved`. `tickets` — в `ostrovok_state`.
- Компания: `GET /api/company/tickets` (входящие, отдельная страница `web_debug/company.html`) + webhook `COMPANY_WEBHOOK_URL` через тот же `outbox` с повторами (3 попытки, экспоненциальная пауза); без URL — только входящие.
- Срочное: кроме обращения агент сразу предлагает, что может сам (другой отель на сегодня — конвейер с датами «сегодня–выезд»; другой рейс — `check_road`) кнопками.
- Карточка `present.complaint`: без шуток, сочувствие одной фразой, номер обращения и срок ответа — из результата мока. Проверка `promise_claim` расширяется: «вернём деньги», «компенсируем», «гарантирую» — нельзя.
- Смена статуса обращения → `outbox` `ticket_update` → сообщение человеку.

Тесты: обращение создаётся с контекстом заказа; срочность; без шуток; без обещаний; webhook с повторами; входящие компании.

### W8. Бенчмарк v4 и данные (параллельно с W1–W7, ~3 ч на написание + прогоны)

- Бриф v4 (`evals/bench/v4/BRIEF.md`) для внешней модели (GPT-6.1 через Codex, как v3): 
  - 25 первых ходов «не знаю куда» у **нового** человека с месяцем и городом вылета: скрытые требования (тип отдыха, бюджет, климат, ограничения дороги) → метрика попадания в топ-3 (решение 31);

- `evals/predicates.py`: `hit_at_3` (кодом по скрытым требованиям), `no_history_claim`, `deal_consistent`, `ticket_created_with_order`, `no_promise`.
- Отчёт: попадание в топ-3 (новый / вернувшийся отдельно), доход до корзины (вторичная, без порога), точность диспетчера, доля deep, p50/p95 fast и deep, стоимость хода по путям.

### W12. Цифры только метками (решение 36, ~5–6 ч, до W3/W5/W6/W7 — они пишут новые карточки уже по этому правилу)

- `agent/slots.py`: словарь меток хода `{"price:v2": 48700, "out_hours:v2": 3.8, "dates:v2": ("2026-11-12", "2026-11-19"), "nights:v2": 7, "budget": 150000, "deal_pct:d1": 20, …}` строится кодом из входа карточки (все числа, которые сейчас попадают в `allowed_from`, получают имя); в карточку модели идёт **список меток с примером отрисовки**, а не голые числа.
- `render_slots(text, slots) -> str`: подстановка через `payloads.fmt_rub / fmt_hours / fmt_date_range / fmt_int`; неизвестная метка или метка чужого id → блок `unknown_slot` (один повтор, затем текст кодом).
- `guards.check_card_output`: любая цифра в тексте модели до подстановки → блок `digit_in_text`; `small_int_max` перестаёт действовать; `foreign_number` и `computed_claim` остаются как вторая линия.
- Метка привязана к id: `{price:v2}` в предложении про Анталью, когда `v2` — Хургада, ловится проверкой «название в предложении ↔ id метки» (`slot_mismatch`, блок) — у меток это детерминированно, в отличие от голых чисел.
- Промпты: `present/*.md`, `guide.md`, `voice.md` — правило и 2–3 примера; ответ `understand` не меняется (он читает числа человека в бриф, это понимание, а не текст человеку; проверка патча — как сейчас).
- Evals: 50 из 92 кейсов уровня 2 проверяют `numbers_subset` — утверждение переводится на текст после подстановки + новое `no_digits_raw`; `evals/build_inputs` пересобирает входы.
- На демо и в README: «модель не пишет ни одной цифры — все цифры ставит код» + пример трассы (сырой текст модели с метками → текст человеку).

Тесты: словарь меток из входа каждой карточки; подстановка и формат; цифра в сыром тексте → блок; чужая и неизвестная метка → блок; несоответствие названия и id → блок; кодовый запасной текст без меток.

### W10. GIF и эмодзи (~2 ч)

- GIF: `server.py` принимает `image/gif`; первый кадр (и при многих кадрах ещё один из середины) → PNG через Pillow (`pillow==13.0.0`, добавлен) → существующий путь фото (`image_match`).
- Эмодзи: таблица `rules.json` `emoji` (🏖️🌊 → sea, 🏔️⛰️ → mountains, ❄️⛷️ → snow, 🏛️ → city/culture, 🌴☀️ → warm, 🍷 → gastro, 👶 → family, 🐕 → pet:dog, 💸 → «недорого»); сообщение только из эмодзи → желания кодом до `understand`; смешанное → подсказка в `understand`. Тесты: таблица, сообщение из одних эмодзи, смешанное.

### W11. Экскурсии и события — синтетика на реальных площадках (~4 ч)

Проба 2026-10-28 (IP вне России): KudaGo → 403, Timepad → 403, Tripster → 401. Решение владельца: живые источники не подключаем, делаем синтетику.

- Площадки — реальные из OSM (`pois` + при необходимости добор в `data_build`: `amenity=theatre|concert_hall|arts_centre`, `leisure=stadium`, `tourism=attraction|museum`).
- Мок: `ostrovok_mcp/events.py`, детерминированные (`seed = sha256(venue|date)`): `{event_id, destination_id, venue_poi_id, kind (concert|show|sport|festival|excursion), title_ru, starts_at, ends_at, price_from_rub, niche_tags}`, `source = synthetic`; нишевые экскурсии — `kind = excursion` с темой (гастро, индустриальная, крыши, ночная…), длительностью и ценой. Инструмент мока `search_events(destination_id, date_from, date_to, kinds?, tags?)`.
- Движок: событие с датой и площадкой → поездка на эти даты, отель рядом с площадкой (`prefs.near` = площадка) с заселением в ночь события, обратная дорога на следующий день; экскурсия — доп в карточке с причиной из брифа и в `place_info`.
- Понимание: «на концерт / на матч / на фестиваль в …» → желание события; «что-нибудь необычное / нишевое» → теги экскурсий.
- Честность: на демо и в карточке — «расписание событий синтетическое».

Тесты: детерминированность генератора; поиск по датам и типам; отель рядом с площадкой; ночь после события покрыта проживанием.
